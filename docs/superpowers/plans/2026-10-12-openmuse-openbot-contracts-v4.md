# OpenMuse on OpenBot: implementation contracts and fixed fixtures (v4 draft)

> Approved planning source for the v4 Ticket catalog. **Target contracts, not implemented APIs.** Values copied from current code are marked **existing**; new values are **target decisions**. An implementing Ticket must preserve these contracts or record a reviewed change before downstream work. Spec: [openmuse#1](https://github.com/1123786563/openmuse/issues/1).

## 1. Build and source boundary

- **Existing:** OpenMuse root uses pnpm 11.19.0 and Node >=22; `pnpm install --frozen-lockfile`, `pnpm build:web`, `pnpm build:ios`, `pnpm build:android`, `pnpm typecheck`. OpenBot root uses Bun 1.3.14; `bun install --frozen-lockfile`, `bun run build`, `bun run typecheck`. OpenBot's root Bun workspace includes `app`, `server`, `worker`; it does not include the OpenMuse client.
- **Target:** OpenBot submodule path `apps/openmuse` points to the entire existing OpenMuse repository. The client entry is `apps/openmuse/apps/mobile`. From an OpenBot clean checkout: `git submodule update --init --recursive`, `cd apps/openmuse && pnpm install --frozen-lockfile && pnpm build:web`; native export uses the corresponding OpenMuse root scripts. OpenBot's normal `bun run build` remains a separate backend build.
- **Source reconciliation:** compare each path under copied `apps/openmuse-mobile` against the canonical `apps/mobile`, including its vendored domain, Metro configuration, tests, lockfiles and assets. Record `copied path / canonical path / difference hash / intent / target Ticket / resolved commit`. No deletion Ticket starts while a row is unresolved.
- **CI acceptance:** a clean checkout records the OpenMuse commit SHA, builds Web and native exports from the submodule, builds OpenBot, and never starts the old OpenMuse server or TaskWorker.

## 2. Identity, private Bot and local session state

- **Existing:** OpenBot `createRequireUser` resolves the Better Auth session into an authenticated actor. `/api/mobile/workspace` reads the current user, accessible Bots and Channels; `/api/mobile/conversations` resolves a permitted Bot to a Channel/Thread. OpenMuse currently uses `POST /api/session`, a Bearer token held in `App.tsx` memory, `MuseApi`, CopilotKit headers, computer preview headers, and PDF download/view headers.
- **Target first-entry contract:** `POST /api/mobile/openmuse-bot` takes no user ID. It returns `{botId, templateVersion, computerProfileId}`; ownership comes from the session. Add a database unique constraint on `(owner_user_id, template_key)` for `template_key=openmuse-private`. On concurrent calls, one insert wins and all callers read the same Bot. `GET /api/mobile/workspace` then returns that Bot. A foreign Bot ID remains a 404.
- **Template ownership:** managed: `templateVersion`, `visibility=private`, `ownerUserId`, allowed tool grants, computer policy/profile, and system prompt revision. User-editable: Bot display name, title, description/role text, avatar and personal tone/preferences. A template revision applies only if `storedVersion < targetVersion`, under compare-and-swap or row lock; two concurrent updates produce one final version. Preview returns `{field, old, new, ownership}` and never proposes overwriting a user-editable value. Fixture: v1 grants `mail.read`; v2 adds `calendar.read` while a user-edited title “Research helper” remains unchanged.
- **Client state inventory:** in-memory session token and `MuseApi` in the current app; CopilotKit runtime/session state; Channel and Thread list/cache; `ComputerDraftProvider` drafts; computer preview/image URL and live stream; PDF viewer URL plus `expo-file-system` cache file named from File ID; current Web/native browser cookies or Better Auth Expo session store. File-level plans must identify every current storage key or cache path before changing it. Target Web uses credentialed HttpOnly session cookies. Target native uses the Better Auth Expo session store rather than the old OpenMuse Bearer token. Logout revokes the session, clears these caches, closes streams, deletes downloaded PDF cache files and prevents a shared-device user B from seeing user A's data. A 401 from `getSession` is the expired-session signal; a client must clear private state and show sign-in.

  | State | Current location found | Target invalidation proof |
  | --- | --- | --- |
  | Old access token and `MuseApi` | `App.tsx` React state; copied into request/CopilotKit headers | Replace with OpenBot session; remount provider on user change |
  | Channel/Thread/chat and computer drafts | React component/context state, including `ComputerDraftProvider` | Clear on logout/401; A→B shared-device flow shows no A title/draft |
  | Computer frame and live stream | Image URI/component memory plus stream socket | Close socket; subsequent A stream URL returns 401/404 |
  | Native PDF download | `expo-file-system` cache directory, current `<fileId>.pdf` filename | Delete downloaded path; A's URL/bytes cannot open after B login |
  | Web browser session | Target Better Auth HttpOnly cookie | Sign-out invalidates cookie and all authenticated media fetches |
  | Native session credential | Target Better Auth Expo secure session adapter; library key is fixed in the I04/I05 file-level plan after SDK inspection | Sign-out clears adapter; `getSession` returns 401 and A→B cannot restore A |

## 3. Conversation and computer contracts

- **Conversation identity:** `{botId, channelId, threadId, runId?}` are distinct IDs. `/api/mobile/conversations` already returns the first three. Channel list is ordered by OpenBot's existing pinned/recency/ID keyset cursor. Archive hides a Channel from the active list; an Archived filter can list and reopen its retained Thread, without changing its `threadId`.
- **Stream resume target:** persist/render each event once by `(threadId, runId, eventId)`. Resume requests events strictly after the last committed `eventId`; if the server cannot replay that cursor, reload the persisted Thread history and show a non-duplicating interruption. Stop is idempotent and reaches `stopped` or `completed`, never an eternal spinner. Fixture: events `e1:text`, `e2:tool-start`, disconnect, replay `e2,e3:tool-result` renders `e2` once and then `e3`. A stop racing with completion leaves one terminal state and one transcript.
- **Tool-event fixtures:** text delta, tool start, tool result, tool error, reviewed-action card, Policy approval card, computer screenshot, browser navigation, mail thread, calendar event, file artifact, and unknown event. Each has a readable UI state; the unknown event is a neutral fallback, not a fabricated success.
- **Computer control:** proposed `viewing → requesting → controlling → released` with `refused` and `expired` outcomes. A control lease binds `userId, botId, streamId, leaseId, expiresAt`. Input requires the active lease and monotonic input sequence. Two concurrent requests cannot both control; transfer requires explicit release or expiry. Logout, disconnect or Policy refusal revokes the lease; any later keyboard/mouse event returns 403/409 and is not delivered. Audit records actor, Bot, lease and decision. Existing OpenBot computer gateway and Policy approval are reused; a new UI does not implement authorization.

## 4. OpenConnector OAuth and Google domain data

- **OAuth state:** target `state` is a random at-least-128-bit one-use value, bound to session user, provider, requested scopes and allowed return URI, expiring after 10 minutes. Callback requires the same active OpenBot user/session; wrong, expired or cross-session state fails without creating a connection. A repeated callback for the same completed state and session returns the recorded connection result without another alias or token exchange; replay in another session fails. `nonce` is used if the provider response includes identity claims. The alias is server-derived via OpenBot's existing personal alias seam, never client-selected.
- **Connection:** `{provider, accountEmail, status, grantedScopes, generation, connectedAt}`. Status is `connected | refresh_required | disconnected | revoked`. Generation increments on reconnect or account change and is embedded in every Reviewed action. A disconnected/revoked/refresh-required connection refuses Mail/Calendar provider calls with a stable 409 response before reaching OpenConnector. Gmail read can depend directly on Gmail consent; Calendar consent is a separate branch. Tokens and client secrets remain in OpenConnector.
- **Mail read DTO:** `{id, threadId, from, to[], subject, bodyText, receivedAt, unread, labels[], attachments:[{id,name,mimeType,size}]}`. List is newest `receivedAt` first, then `id` descending; default 25, maximum 100, opaque owner/connection-bound `nextCursor`. Invalid cursor returns 400; provider truncation returns `truncated=true` and a visible message. Thread messages are oldest first by provider time/ID. Fixture: three messages at equal timestamp return deterministic ID order over page size two, without duplicate or missing item.
- **Calendar read DTO:** `{id, calendarId, etag, title, start, end, allDay, timeZone, location, description, attendees[]}`. List is ascending start then ID, default 50, maximum 100, with owner/connection-bound cursor. The range is half-open `[timeMin,timeMax)` and at most 366 days, matching existing OpenMuse validation. All-day uses date-only start and exclusive date-only end. Fixture LA DST: `2026-03-08T01:30:00-08:00` to `2026-03-08T03:30:00-07:00` lasts one hour and displays 01:30–03:30 in `America/Los_Angeles`; all-day `2026-03-08` to `2026-03-09` displays only March 8. A changed device zone changes presentation, not stored instants.

## 5. File and PDF contracts

- **File:** `{id, ownerUserId, name, mimeType, size, sha256, versionId, parentId?, source, createdAt, deletedAt?}`; byte path is server-derived and never accepted from the client. Proposed general upload ceiling is 20 MiB; PDF retains the existing 10 MiB and 500-page limit. SHA-256 is over original bytes. Version IDs are immutable; rename changes display metadata only; delete tombstones immediately, removes the list item and refuses old URLs. A retried upload with the same owner-scoped idempotency key returns the existing File/version, while a new key creates a new File even with identical bytes.
- **Content access:** authenticated stream or short-lived URL checks current owner and deletion state on every fetch. Foreign ID, old signed URL after logout/deletion, and path traversal refuse. File bytes and metadata remain recoverable during account-deletion grace period using a durable cleanup manifest.
- **PDF:** existing OpenMuse supports AcroForm text and checkbox fields; dropdown, option list and radio are returned as `unsupported` with their field name and reason. Encrypted/XFA/malformed files refuse; text value is a string up to 10,000 characters and checkbox value is boolean. Unknown name or wrong type refuses before writing. `fill` creates a new File version; the original SHA-256 stays unchanged. “Deterministic” means the same source plus field values yields the same **semantic field values and provenance**, not byte-for-byte identical PDF serialization. Fixture: `person.name="Ava"`, `consent=true`, unsupported dropdown `region`; inspection lists all three, fill changes only the first two, and the original remains blank.
- **Workspace transfer:** the target is a generated path under the private Bot workspace using `fileId/versionId`; the client supplies no arbitrary destination. If a same-name file exists, use a distinct generated path rather than overwrite. Retry with the same transfer key returns the same workspace artifact; partial upload is cleaned or marked failed and never reported as complete.

## 6. Reviewed action contract

- **Proposal:** `{id, ownerUserId, kind, canonicalPayload, payloadHash, accountEmail, connectionGeneration, targetId?, targetVersion?, attachmentVersionIds[], expiresAt, status}`. Existing OpenMuse uses 30-minute expiry; retain that value. Canonical payload includes recipients/subject/body or calendar/time-zone fields, and reply `threadId/replyToMessageId`. A proposed attachment binds its immutable File version.
- **States:** `awaiting_review → denied | expired | cancelled | executing`; `executing → succeeded | failed | outcome_unknown`. Only an atomic compare-and-swap claim may enter `executing`. A repeated decision returns the settled record; it does not call the provider again. Changed hash/account/generation/target version returns 409 and requires a new proposal.
- **Provider attempt:** one durable `attemptId` and provider request fingerprint per claim. Definite provider rejection before submission may become `failed`; timeout or connection loss after submission becomes `outcome_unknown`. No automatic retry from `outcome_unknown`. Human reconciliation records `confirmed_succeeded | confirmed_not_sent | unresolved` plus evidence and reviewer; only confirmed-not-sent can create a fresh proposal, never reuse the claimed attempt. Receipt contains provider message/event ID when known, request fingerprint, decided/attempted/completed times and reconciler.
- **Fixed failure matrix:** deny → zero provider calls; expiry at `expiresAt` → 409/expired; two simultaneous approve calls → one attempt; account generation changes → 409/stale; calendar etag changes → 409/stale; timeout after provider accepted → `outcome_unknown` and zero replay; operator confirms provider ID → `succeeded` with receipt; operator cannot verify → unresolved warning remains.

## 7. Task, Monitor and personal context

- **Task minimum:** `{id,ownerUserId,botId,kind,status,createdAt,updatedAt,attempts,steps[],evidence[],artifactIds[]}`. Existing OpenMuse kinds: agent/document/monitor/finance/plan. Existing statuses: queued/running/waiting_approval/waiting_input/scheduled/paused/succeeded/failed/cancelled. Step statuses: pending/running/succeeded/failed/waiting. Evidence kinds: mail/file/web/user. Run events: plan/step/observation/approval/result/error/status. New OpenBot module reuses `WorkQueue.offer/claim/renew/release/finish` and its database-clock lease; it does not create a second lease system.
- **Small first path:** a one-step agent Task records `queued → running → succeeded` or `failed` within a configurable per-run deadline; the client can close after start. A headless Bot turn uses owner+private Bot context. The first implementation ticket need not support every Task kind or every control transition.
- **Control transitions:** `queued|scheduled|paused → cancelled`; a running Task sets an internal `cancellationRequested` flag, keeps public status `running`, then reaches `cancelled` after its current safe step; `queued|running|scheduled → paused` at a safe step; `paused → queued` on resume; `failed → queued` only as a new attempt; terminal succeeded/cancelled never resume. An illegal transition returns 409 with current status. Lease loss before any external effect can requeue; after an unconfirmed external effect it records a reconciliation wait or failure rather than replay.
- **Human wait:** `{waitId,taskId,kind:input|review,question,fields?,createdAt,answeredAt?}`. Answer requires owner, exact waitId and schema. First valid answer atomically consumes; repeat returns the stored result without advancing twice; malformed answer returns 400 and leaves the wait open.
- **Plan:** step `{id,title,dependsOn[],status,result?,evidenceIds[]}`; only steps whose predecessors succeeded run. Failed step remains failed, successors remain pending until explicit retry/new attempt; succeeded steps are not replayed.
- **Monitor:** reuse OpenMuse `change|contains|price_below` and interval 1–10,080 minutes. Schedule uses UTC database time, with `nextCheckAt` stored; a due check is at-or-after that instant. Observation identity is `sha256(monitorId + normalizedSource + normalizedValue)`; cursor is the last committed observation ID/time. Failure backoff is 15, 30, 60 minutes, capped at 6 hours, reset on success. A new condition match emits one `monitor.matched` notification keyed by observation ID; a repeated observation emits none.
- **Task notifications:** `task.succeeded`, `task.failed`, `task.waiting_input`, `task.waiting_review`, `monitor.matched`. Key is `userId/taskId/eventKind/attemptOrObservationId`; each has per-user `readAt`. These events must be emitted by the owning Task/Monitor transition, not inferred by client polling.
- **Finance fixture:** existing parser requires `date,description,amount,category`, 1–5,000 rows, up to 500 KB, ISO date and max two decimals; positive = expense, negative = income, no currency conversion. Fixture rows `2026-09-01,Salary,-4200.00,Income`; `2026-09-02,Groceries,84.50,Food`; `2026-09-03,Coffee,6.50,Food` give income 4200.00, spending 91.00, saved 4109.00, Food 91.00, count 3. A bad amount `6.501` at row 4 refuses the entire CSV with row number; no partial tracker.
- **Goal:** use existing `{id,title,description,category,status,milestones[]}`; an authorized private Bot tool returns exact Goal ID/title/milestone status. **Idea:** `{id,title,reason,evidence[],prompt,kind,input,status,taskId?}`; an accepted Idea points to one Task. **Memory:** `{id,text,source,createdAt}`; retrieval is triggered by explicit private Bot tool call and returns ID/text/source, not a subjective “useful” result. Another Bot and another user receive no record; delete/revoke removes it from subsequent retrieval.

## 8. Activity item contract

- Feed item: `{id,type,sourceId,createdAt,status,title,detail,allowedActions[],readAt?}`. Types are `policy_approval | reviewed_action | task_notification`; `sourceId` names the owning OpenBot record. Sort descending `createdAt`, then `id`; default page 25, maximum 100, with owner-bound cursor.
- Policy approval statuses come from OpenBot's policy store and allow only its own approve/deny operations. Reviewed action uses §6 statuses and allows approve/deny only while `awaiting_review`; `outcome_unknown` allows view/reconcile by an authorized operator, not retry. Task notification allows `mark_read` only. Sending the wrong decision type returns 409 and leaves both source records unchanged.
- A stale client item is re-read from its source before a decision; the response returns current status. Fixture: a reviewed mail proposal expires while Activity is open; its approve button disappears and an attempted stale approve returns 409/expired. A Policy approval card can be denied without changing that Reviewed action.

## 9. Deletion manifest and evidence

- **Module lifecycle seam:** every module that creates user-owned state implements `disableOwner(userId): Promise<void>`, `enumerateOwner(userId): Promise<ResourceRef[]>`, `restoreOwner(userId): Promise<void>`, and `purgeResource(ref): Promise<void>` as appropriate. `ResourceRef` contains `kind,id,externalKey?`. The module's own Ticket provides focused checks for its hook; D04–D08 coordinate already-tested hooks. A module with no restorable external credential states that explicitly rather than fabricating restoration.
- A durable deletion marker `{userId,disabledAt,restoreUntil,phase,resources:[{kind,id,externalKey?,state,lastError?}]}` is written before revoking access. Every state-owning module supplies a list and cleanup hook. Enumerate external File object keys and OpenConnector aliases **before** relational metadata is deleted. Resource states: `pending → deleted` or `retryable_error`; repeat cleanup is idempotent. Retain the manifest until every resource is deleted and backup retention has elapsed. Immediate authorization checks consult the disabled marker; cleanup lag never reopens access.
- Restoration within 30 days covers Bot profile, Channel/Thread, Tasks/steps/evidence, Files/versions, Goals, Ideas, Memory, notifications and unresolved Reviewed actions as read-only history. Queued/running Tasks and all external writes remain cancelled; restoration does not resume them. After `restoreUntil`, restore returns 410.
- Evidence ID format: `<ticket>/<platform>/<case>`. Every acceptance case records precondition fixture/account, action sequence, expected UI, expected API/persisted state, observed result, sanitized screenshot/log/receipt path, code revision and date. A failure names its owning implementation Ticket and blocks only the affected acceptance case plus any downstream signoff. Fixes rerun the failed case and directly related cases; final signoff maps all 43 Spec stories to passed evidence IDs.

## 10. Reference deployment configuration and failure signals

These are **approved v4 planning defaults** for the 1–20 active-user self-hosted profile, not claims about current capacity. Capacity tickets may revise them only with measured evidence and a corresponding update to their acceptance cases.

| Setting or signal | Proposed value / trigger | Expected observable result |
| --- | --- | --- |
| Active private computers | Maximum 20 | 21st start queues or returns a capacity response; no Bot reuses another user's computer |
| Computer idle stop | 15 minutes without run or human control | Workspace state persists; stream closes cleanly |
| Computer workspace disk | 2 GiB per private Bot | Write above limit refuses with a visible quota error |
| Concurrent Task workers | 4 | Fifth runnable Task remains queued and visible |
| Active Tasks per user | 100, matching current OpenMuse service limit | 101st active Task creation returns 409 with the existing limit message |
| WorkQueue attempts | 5, matching OpenBot's existing default | Terminal exhausted item remains inspectable; no silent retries |
| One-step Task acceptance deadline | 300 seconds | Timeout yields failed Task with cause; it does not claim success |
| Connector refresh failure | Any refresh failure | Connected-account status becomes refresh_required; operator signal contains no token |
| Stuck Task | Runnable queued >5 minutes or expired lease without recovery >1 minute | Owner sees delayed state; operator sees Task ID and queue reason |
| Uncertain Reviewed action | Any outcome_unknown | Owner sees warning; operator sees attempt ID and reconciliation status |
| Cleanup retry | Any retryable_error row past next retry time | Operator sees resource kind, safe ID and last error; no secret/byte payload |
